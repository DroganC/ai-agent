# 前端路由与跳转审查

> 审查范围：`src/` 下路由配置及所有跳转逻辑（不含后端 app/）。

## 一、路由结构概览

- **认证**：未登录访问需鉴权页时，`AuthGuard` 重定向到 `/login-callback`，并带 `state.from`；登录成功后跳回 `from` 或 `/home`。
- **Tab 壳**：`TabLayout` 仅包裹 `home`、`rank`、`me`，底部 Tab 仅在这三个路径显示。
- **栈页**：`levels`、`level/:id/*`、`store`、`store/orders`、`learning` 为独立全屏页，不渲染 TabLayout，通过返回或入口跳转。

## 二、已发现的合理设计

1. **兼容重定向**：`/hall`→`/home`、`/leaderboard`→`/rank`、`/profile`→`/me` 保持旧链接可用。
2. **关卡主流程**：首页/关卡列表 → `level/:id/prepare` → 创建 attempt → `level/:id/play`（带 `state.attemptId`）→ 游戏内完成 → `level/:id/pass` 或 `level/:id/settlement`，再试/返回列表逻辑清晰。
3. **个人页快捷入口**：Profile 内「学习中心」「积分商城」跳 `/learning`、`/store`，与路由一致。
4. **404**：`*` 统一到 `/home`，避免白屏。
5. **游戏内 onExit**：各游戏组件的 `onExit` 统一回到 `level/:id/prepare`，与 `LevelPlay`/`GamePlay` 传入的 navigate 一致。

## 三、问题与建议

### 1. Hall 页面成为死代码（低）

- **现象**：路由中 `/hall` 已配置为 `<Navigate to="/home" replace />`，`src/pages/Hall/index.tsx` 从未被渲染。
- **影响**：Hall 组件及样式、逻辑长期不参与运行，易造成误解与冗余维护。
- **建议**：
  - 若确定不再使用「大厅」独立页：删除 `pages/Hall/` 及 `pages/index.ts` 中的 `Hall` 导出，并保留 `/hall` 重定向到 `/home`。
  - 若计划保留为后续入口：在 `router.tsx` 或本文件内注明「Hall 暂未挂载，/hall 重定向到 /home」。

### 2. 双入口「游戏内页」：`/game/:gameId/play` 与 `level/:id/play`（中）

- **现象**：
  - `/game/:gameId` 已通过 `RedirectGameToLevelPrepare` 重定向到 `level/:gameId/prepare`，与主流程一致。
  - `/game/:gameId/play` 仍直接渲染 `GamePlay`，与 `level/:id/play` 的 `LevelPlay` 功能重叠（都是拉关卡 + `renderGame`）。
  - **关键差异**：从 `LevelPrepare` 进入 `LevelPlay` 时会带 `location.state.attemptId`；而从外部或直链进入 `GamePlay` 时没有创建 attempt，故 **没有 attemptId**。
- **影响**：
  - 在 `GamePlay` 下完成游戏时，LinkMatchGame / StepsGame / ClassifyChallengeGame 等依赖 `attemptId` 的组件会走「无 attemptId」分支：不调用 `settleAttempt`，且多数会 `onExit()` 回到准备页，而不是进入通关/结算页。
  - 用户从「关卡准备页 → 开始挑战」与从「直链 /game/:id/play」进入，完成同一游戏后的跳转行为不一致（前者进 pass/settlement，后者回 prepare）。
- **建议**：
  - **方案 A（推荐）**：将 `/game/:gameId/play` 也重定向到 `level/:gameId/play`，并在 `LevelPlay` 内对「无 attemptId 且有关卡 game_type」的情况做明确处理（例如提示「请从关卡准备页开始」并跳回 `level/:id/prepare`），这样只保留一套「游戏内页」逻辑。
  - **方案 B**：若需保留 `/game/:gameId/play` 作为免准备页的入口（如运营链接），则在 `GamePlay` 内进入前先调用创建 attempt 的接口，把得到的 `attemptId` 通过 `location.state` 或 context 传给游戏组件，使结算与跳转与 `LevelPlay` 一致；同时在路由或注释中注明「主流程以 level 为准，game/play 为带 attempt 的快捷入口」。

### 3. 非 Tab 页时底部 Tab 高亮（低）

- **现象**：在 `/levels`、`/store`、`/learning` 等非 Tab 页时，`BottomTab` 的 `activeKey` 使用 `uiStore.tab || '/home'`，因此仍会高亮某个 Tab。
- **影响**：用户可能误以为当前还在某个 Tab 页内，属于体验细节。
- **建议**：可接受；若希望更一致，可在非 Tab 路径下将 `activeKey` 设为 `null` 或单独「无高亮」状态，避免误判（需确认 UI 设计是否支持无高亮）。

### 4. Settlement 重试使用整页刷新（低）

- **现象**：`Settlement` 中 `onRetry` 使用 `navigate(0)`，即整页刷新。
- **影响**：能重新拉取数据，但会丢失前端状态并重新加载整应用。
- **建议**：若希望更轻量，可改为对当前路由做 `replace` 或重新请求本页数据后 setState；保留 `navigate(0)` 也可接受，作为简单兜底。

## 四、跳转路径汇总（便于核对）

| 来源 | 目标 | 说明 |
|------|------|------|
| AuthGuard（未登录） | `/login-callback` + state.from | 登录后回 from 或 /home |
| LoginCallback | `from` 或 `/home` | replace |
| TabLayout index | `/home` | replace |
| Home | `level/:id/prepare`、`/levels`（含 state.focusSearch） | 关卡入口、关卡列表 |
| Levels | `level/:id/prepare`、`navigate(-1)` | 关卡卡片、返回 |
| LevelPrepare | `level/:id/play`（state.attemptId）、`navigate(-1)` | 开始挑战、返回 |
| LevelPlay | `level/:id/prepare`、`level/:id/settlement`、`navigate(-1)` | 缺 attemptId 时回准备；步骤流完成进结算 |
| GamePlay | `level/:gameId/prepare`（onExit） | 仅 onExit，无 attemptId |
| LinkMatchGame / StepsGame | `level/:id/pass`（state.attemptId） | 需从 LevelPlay 进入才有 attemptId |
| ClassifyChallengeGame | `level/:id/pass` 或 `level/:id/settlement`（state.attemptId） | 同上 |
| LevelPass | `level/:id/prepare`、`/levels` | 再挑战、返回列表 |
| Settlement | `level/:id/prepare`、`/levels`、`navigate(0)`（重试） | 再试、列表、刷新 |
| Store | `navigate(-1)`、`/store/orders` | 返回、兑换记录 |
| StoreOrders | `navigate(-1)` | 返回 |
| Profile | `/learning`、`/store` | 快捷入口 |
| RedirectGameToLevelPrepare | `level/:gameId/prepare` 或 `/levels` | gameId 缺失时回列表 |

## 五、结论与优先建议

- **建议优先处理**：双入口导致的 **`/game/:gameId/play` 与 attemptId 不一致**（见 三.2），避免同一游戏两种完成路径行为不同。
- **可选清理**：Hall 死代码（三.1）做删除或注释说明。
- **其余项**：为体验与可维护性优化，可按迭代安排处理。
