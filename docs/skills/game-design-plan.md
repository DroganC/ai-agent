# 通用游戏设计计划 Skill

本文档是从具体小游戏规格中抽离的**可复用骨架**：用于撰写任意「学习型 / 关卡型」小游戏的设计与实现计划。填空即可落地到评审、排期与实现。

---

## 1. 文档目的

用一份计划回答：

- **玩什么**（核心循环与规则）
- **怎么赢 / 输 / 放弃**
- **与学习目标、业务如何结合**
- **如何接入现有工程**（类型、路由、组件、结算）
- **如何分期交付**（MVP → 完整 → 增强）

读者应能据此做技术评审、估改动面、拆任务，并与产品 / 教研对齐验收标准。

---

## 2. 推荐章节结构（按顺序）

| 章节 | 要回答的问题 | 通用要点 |
|------|----------------|----------|
| 玩法简介 | 一句话是什么？核心循环？ | 终端（移动 / 桌面 / 横竖屏）、布局原则（居中、安全区、动态列数等） |
| 学习目标与能力 | 学完 / 玩完得到什么？ | 知识维度、认知能力（推理、记忆、风险判断等） |
| 接入方式 | 在项目里怎么挂上去？ | 类型枚举、路由、关卡字段、`renderGame` 分支、懒加载、目录约定 |
| 规则详述 | 参数、状态机、边界 | 可调参数表、实体类型与状态表、子挑战规则、胜负与退出 |
| 边界、异常与平台行为 | 坏了、断了、用户乱点时怎样？ | 见 §5 |
| 数据与内容 | 关卡配什么、题从哪来？ | TS 类型、配置字段、题库组织、随机 / 去重规则 |
| 内容与运营 | 谁维护、多少算够？ | 见 §6 |
| 交互与 UI | 长什么样、怎么操作？ | 线框或结构说明、状态栏、关键组件、视觉状态表 |
| 无障碍与触控 | 谁都能用吗？ | 见 §7 |
| 埋点与结算 | 进度怎么记、怎么算分？ | 事件、`step_id`、结算字段、跳转结算页 |
| 成功指标 | 上线后看什么数？ | 见 §8 |
| 技术实现 | 目录、状态、核心算法 | 组件树、核心类型、算法清单、与现有 UI / Hooks 对齐 |
| 分期实现 | MVP → 完整 → 增强 | 每阶段「必做 / 可砍 / 后置」 |
| 验收标准（Definition of Done） | 怎样算做完？ | 见 §9 |
| 风险与未决问题 | 还有什么没定？ | 见 §10 |
| 测试与 Mock | 怎么本地跑通？ | Mock 数据、最小关卡样例 |
| 一页总结表 | 给评审快速扫 | 终端、类型名、核心机制、接入点、实现顺序 |

## 3. 每个计划应显式写清的「通用决策」

1. **核心循环**：探索 → 触发学习（答题、分类、配对等）→ 反馈 → 推进局面。
2. **风险与学习绑定**：高风险步骤是否绑定「多题连续、错一即终局」等，单独说明。
3. **参数化**：行数、题量、限时、特殊格数量等用**表格**列出默认值与含义，避免散落在正文。
4. **状态完备性**：每种实体的**互斥状态**（未翻开、已翻开、标记、中断中等）及**禁止操作**（如标旗格是否可点）。
5. **多端差异**：长按 / 右键 / 键盘等行为在移动与桌面是否不同，写在一处。
6. **架构契约**：`GameRenderProps`、`Page` / `PageHeader`、倒计时 Hook、结算与 `attemptId` 流转，列「必须与现有项目一致」的清单。
7. **分期**：MVP 只保证「能玩通 + 主规则」；埋点、限时、皮肤、专题题库可后置，并在文档中标出。

## 4. 可复制的小节模板（填空用）

### 4.1 玩法简介

- 游戏名 + 与经典玩法的关系（若有）。
- 场景规模（棋盘、关卡数、动态或固定尺寸）。
- 实体类型与各类型操作结果（列表）。
- 学习目标一句话 + 可选主题 / 行业（如安全培训、产品知识）。

### 4.2 学习目标与能力

- **知识**：覆盖哪些知识点或标签。
- **能力**：逻辑推理、记忆、风险判断、手眼协调等（按需勾选并一句话说明如何体现在玩法里）。

### 4.3 接入方式

- `game_type` 或等价字段取值。
- 类型定义路径、路由模式、`renderGame`（或等价入口）分支名、懒加载组件名、建议新建目录。

### 4.4 规则详述

- **参数表**：可调项 + 默认值 + 说明。
- **类型与状态表**：外观、操作、结果。
- **子挑战**（若有）：触发条件、题量、通过 / 失败、对局面的影响。
- **胜利 / 失败 / 放弃**：含顶部返回、底部退出、是否二次确认、`aborted` 等。

### 4.5 数据与内容

- `Question` / `LevelConfig` 等最小字段集。
- 题库：分类维度、抽取规则、选项打乱、同局去重（可选）。

### 4.6 交互与 UI

- 单屏结构（标题 / 状态栏 / 主区 / 吸底）。
- Modal / Dialog 种类与统一动效、宽度、安全区（`safe-area-inset`）。
- 关键视觉状态表（颜色可与设计系统对齐，不必写死色值）。

### 4.7 埋点与结算

- 与现有 `sendEvents` / `settleAttempt`（或等价 API）对齐的事件列表与 `step_id` 约定。
- 结算字段：`status`、`score`、`duration_ms`、`fail_reason`、`error_count` 等。
- 建议**计分维度表**（可标「可选」）。

### 4.8 技术实现

- 目录与文件职责。
- 核心类型与游戏状态要点。
- 算法列表（初始化、展开、重算、胜负判定等）。
- 与现有组件库、样式方案（如 CSS Modules + Less）一致。

### 4.9 分期实现

- **阶段一（MVP）**：类型 + 路由 + 主流程 + 最小 UI。
- **阶段二**：完整规则 + 埋点 + 限时 + 退出确认等。
- **阶段三**：内容扩展、难度、动效、后端配置、数据可视化等。

### 4.10 测试与 Mock

- Mock 关卡、`game_type`、attempt 接口是否与现有 `mocks` 一致。
- 最小可运行数据集规模说明。

### 4.11 一页总结表

| 项目 | 说明 |
|------|------|
| 终端 | 如：仅移动端竖屏 |
| 游戏类型 | 枚举值 |
| 核心机制 | 一两句话 |
| 与现有架构 | Level、Attempt、renderGame、结算 |
| 实现顺序 | MVP → … |

## 5. 边界、异常与平台行为

写作时至少覆盖以下条目（不适用的标注 N/A）：

| 场景 | 建议写明 |
|------|----------|
| 无网 / 接口失败 | 是否重试、Toast 文案、是否阻断进入游戏 |
| 题目加载失败 | 降级（内置题）或整关失败 |
| `attemptId` 缺失 | 是否允许玩、是否仅本地模式 |
| 重复进入同一关 | 新 attempt 还是复用 |
| 浏览器 / App 返回键 | 与「顶部返回」行为是否一致 |
| 倒计时 + 切后台 | 暂停、继续或照常扣时（移动端必写清） |
| 横竖屏旋转 | 是否锁定、布局是否重排 |

---

## 6. 内容与运营

| 条目 | 说明 |
|------|------|
| 题库最小规模 | 如首版至少 N 题，保证随机不「穿帮」 |
| 维护方式 | 静态文件 / CMS / 后端配置 |
| 更新频率与责任人 | 可选 |
| 解析与错题本 | 首版是否展示解析 |
| 版权与审核 | 引用材料是否需法务 / 教研审核 |

---

## 7. 无障碍与触控

| 条目 | 说明 |
|------|------|
| 色觉 | 状态不仅依赖颜色（图标 / 文案 / 形状） |
| 字号与对比度 | 题目区、按钮是否满足可读下限 |
| 触控热区 | 棋盘格、按钮最小点击区域（如 ≥44px） |
| 动效 | 是否提供「减少动效」或与系统设置一致（若项目已有规范则引用） |

---

## 8. 成功指标（上线后）

除埋点事件外，建议列 **1～3 个**可讨论的业务或学习指标，例如：

- 关卡完成率、平均用时
- 答题正确率、重复游玩率
- 与培训目标相关的代理指标（按需）

用于判断玩法是否「达到学习目标」，而非仅「能跑」。

---

## 9. 验收标准（Definition of Done）

用**可测试的陈述**写 3～8 条，覆盖主路径与关键边界，例如：

- [ ] 首次触发某类挑战并全部答对后，局面变化符合规则（状态 / 计分 / 重算）。
- [ ] 答错一题时游戏结束方式与文案符合规则；地雷 / 答案暴露行为符合文档。
- [ ] 胜利条件在拆雷 / 转化安全格等动态变化后仍正确。
- [ ] 退出确认与 `aborted` 结算与文档一致。
- [ ] 埋点事件与 `settleAttempt` 字段与现有后端约定一致（若本阶段包含）。

避免仅写「完成开发」，应能据此做 QA 勾选。

---

## 10. 风险与未决问题

单独一节列出**尚未拍板**的事项，例如：

- 题量不足或类目不均衡
- 是否必须后端配题才能上线
- 是否灰度发布、`game_type` 是否需要 feature flag
- 设计稿 / 音效 / 翻译到位时间

降低「文档看起来很完整、实现时不断改需求」的成本。

---

## 11. 可选增强（按需加入计划）

| 主题 | 说明 |
|------|------|
| Feature flag | 新玩法如何灰度、如何一键关闭 |
| 国际化 | 文案 key 约定、RTL、日期数字格式 |
| 性能预算 | 首屏、重绘、Modal 打开在低端机上的预期 |
| 测试策略 | 纯函数单测范围、E2E smoke 范围 |
| 安全与合规 | 学时认定、审计日志、成绩导出（培训场景常见） |
| 依赖与协作 | 依赖后端字段、设计、音效的清单及阻塞关系 |
| 文档元信息 | 作者、日期、修订摘要（计划会迭代时有用） |

## 12. 质量自检清单

- [ ] 新人能否从「接入方式」定位到要改的文件？
- [ ] 胜负与「中途退出」是否都有定义？
- [ ] 关卡配置能否覆盖文档中全部可调参数？
- [ ] MVP 是否明确砍掉了什么，避免范围蔓延？
- [ ] 埋点 / 结算字段是否与现有代码或接口文档命名一致？
- [ ] 「边界与平台行为」是否写过一遍？
- [ ] 是否有一条「验收标准」能直接交给 QA？
